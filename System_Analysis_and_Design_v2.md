## 📊 System Analysis & Design Documentation (ThreatScopeLab)

### 1. System Analysis & Design

#### 1.1 Problem Statement & Objectives

> [!WARNING]
> **The Problem:** The default posture of most security monitoring deployments is reactive: analysts wait for alerts generated by pre-packaged vendor rules and respond to what has already been flagged. This model has a critical structural blind spot - it cannot tell you what adversarial techniques your existing ruleset fails to detect.

> [!TIP]
> **The Solution:** ThreatScopeLab exists to close that gap. By coupling a controlled adversary emulation engine (**Atomic Red Team**) with a purpose-built SIEM (**Wazuh**), this project constructs an iterative validation loop where every custom detection rule is authored in direct response to observed telemetry from a live attack simulation.

**Design Philosophy**
* 🔴 **Red Team Focus:** Every rule in the `/wazuh_rules` repository has a corresponding emulation plan that proves it works.
* 🔵 **Blue Team Focus:** The project deliberately prioritizes detection coverage validation over incident response automation.
* 🗺️ **Visibility:** Coverage is measured against the MITRE ATT&CK framework not a checklist, but a live heatmap.

**Scope Boundaries**

| 🟢 In Scope | 🔴 Out of Scope |
| :--- | :--- |
| Wazuh-based SIEM deployment and custom rule authoring | Commercial EDR or third-party SOAR integration |
| Atomic Red Team emulation on Windows 11 & Ubuntu 22.04 | Real-world threat actor infrastructure emulation |
| MITRE ATT&CK technique mapping and coverage visualization | Automated incident response (SOAR playbooks) |
| Sysmon-augmented telemetry collection on Windows | Forensic disk image acquisition or memory analysis |
| Custom rule validation via re-execution testing | Production network deployment or live threat hunting |

#### 1.2 Functional & Non-Functional Requirements

> [!IMPORTANT]
> **Functional Requirements** map the explicit capabilities the platform must deliver.

| ID | Category | Requirement | Priority |
| :--- | :--- | :--- | :--- |
| **FR-01** | Log Ingestion | Wazuh Agent on each endpoint SHALL forward logs to the Wazuh Manager in real time over TLS-encrypted channel (port 1514). | 🔴 Critical |
| **FR-02** | High-Fidelity Logging | Sysmon SHALL be deployed on Windows 11 endpoints with SwiftOnSecurity config to capture Event ID 1, 3, and 11. | 🔴 Critical |
| **FR-03** | Rule Matching | The Wazuh Rule Engine SHALL parse incoming logs against custom XML rules in `local_rules.xml` on every event ingestion cycle. | 🔴 Critical |
| **FR-04** | Alert Generation | When a custom rule matches an event, the system SHALL generate an alert with a severity level, MITRE ID, agent hostname, and timestamp. | 🔴 Critical |

> [!NOTE]
> **Non-Functional Requirements** dictate the system's operational constraints.

| ID | Category | Requirement |
| :--- | :--- | :--- |
| **NFR-01** | Performance | Sustain at least 1,000 EPS (Events Per Second) under emulation load without dropping events or introducing alert latency above 5 seconds. |
| **NFR-02** | Isolation | The virtual lab network SHALL be isolated from the host network. No emulation traffic SHALL egress the configured VMnet segment. |
| **NFR-05** | Precision | Custom rules SHALL be authored to minimize false positives. Target behavioral signatures rather than static filename IOCs. |

### 2. Database Design & Data Modeling

#### 2.1 Logical Schema

> [!CAUTION]
> In the Wazuh deployment, most of this data is stored in the OpenSearch index (JSON documents). This relational schema is provided as a conceptual model for documentation and coverage tracking purposes.

**EVENT**
| Column | Type | Description | Constraint |
| :--- | :--- | :--- | :--- |
| `event_id` | UUID | Unique event identifier | PK, NOT NULL |
| `agent_id` | UUID | Source agent reference | FK -> AGENT, NOT NULL |
| `log_source` | VARCHAR(100) | Source log channel (e.g., Sysmon/Operational) | NOT NULL |
| `sysmon_event_id` | INTEGER | Sysmon Event ID (1 = Process Create, etc.) | NULLABLE |
| `command_line` | TEXT | Full commandLine field from Sysmon Event ID 1 | NULLABLE |

**ALERT**
| Column | Type | Description | Constraint |
| :--- | :--- | :--- | :--- |
| `alert_id` | UUID | Unique alert identifier | PK, NOT NULL |
| `rule_id` | INTEGER | Matched rule reference | FK -> CUSTOM_RULE, NOT NULL |
| `alert_level` | INTEGER | Inherited severity from matched rule | NOT NULL |
| `status` | ENUM | Triggered / Acknowledged / Investigating / MappedToMITRE / Resolved / False Positive | DEFAULT 'Triggered' |

### 3. Data Flow & System Behavior

#### 3.1 Alert Lifecycle (State Transitions)

> [!NOTE]
> Alerts in ThreatScopeLab have a well-defined lifecycle. Understanding these transitions is essential for SOC Analysts operating the platform.

| From State | Trigger | To State | Actor Responsible |
| :--- | :--- | :--- | :--- |
| `[Initial]` | Wazuh rule match on incoming event | **Triggered** | 🤖 SIEM System |
| `Triggered` | Analyst opens alert in dashboard | **Acknowledged** | 🕵️ SOC Analyst |
| `Acknowledged` | Analyst begins raw log deep-dive | **Investigation Open** | 🕵️ SOC Analyst |
| `Investigation Open` | Emulation source confirmed in logs | **MappedToMITRE** | 🕵️ SOC Analyst |
| `Investigation Open` | Alert from benign activity | **False Positive** | 🕵️ SOC Analyst |
