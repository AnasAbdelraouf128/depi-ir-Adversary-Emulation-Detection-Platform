# 🛡️ DEPI Graduation Project: Adversary Emulation & Detection Platform
## 📊 System Analysis & Design Documentation (ThreatScopeLab)

### 1. System Analysis & Design

#### 1.1 Problem Statement & Objectives

> [!WARNING]
> **The Problem:** The default posture of most security monitoring deployments is reactive: analysts wait for alerts generated by pre-packaged vendor rules and respond to what has already been flagged. This model has a critical structural blind spot - it cannot tell you what adversarial techniques your existing ruleset fails to detect.

> [!TIP]
> **The Solution:** ThreatScopeLab exists to close that gap. The core thesis is simple: you cannot trust a detection you have never deliberately tried to break. By coupling a controlled adversary emulation engine (**Atomic Red Team**) with a purpose-built SIEM (**Wazuh**), this project constructs an iterative validation loop where every custom detection rule is authored in direct response to observed telemetry from a live attack simulation.

**Design Philosophy**
* 🔴 The project deliberately prioritizes detection coverage validation over incident response automation.
* 🛡️ Every rule in the `/wazuh_rules` repository has a corresponding emulation plan that proves it works.
* 🗺️ Coverage is measured against the MITRE ATT&CK framework not a checklist, but a live heatmap.

**Core Objectives**
* Deploy a fully isolated, reproducible lab environment capable of safely executing known adversarial TTPs (Tactics, Techniques, and Procedures).
* Author high-fidelity Wazuh XML detection rules triggered by specific behavioral signatures - not just process names or static IOCs.
* Map every engineered detection to a specific MITRE ATT&CK technique ID, producing a measurable visibility layer.
* Transition the SOC operational model from alert-reactive to emulation-validated, demonstrating the detection engineering lifecycle end-to-end.
* Produce a reproducible, documented lab that a third party can deploy and extend using the provided README and emulation plans.

**Scope Boundaries**

| 🟢 In Scope | 🔴 Out of Scope |
| :--- | :--- |
| Wazuh-based SIEM deployment and custom rule authoring | Commercial EDR or third-party SOAR integration |
| Atomic Red Team emulation on Windows 11 & Ubuntu 22.04 | Real-world threat actor infrastructure emulation |
| MITRE ATT&CK technique mapping and coverage visualization | Automated incident response (SOAR playbooks) |
| Sysmon-augmented telemetry collection on Windows | Forensic disk image acquisition or memory analysis |
| Custom rule validation via re-execution testing | Production network deployment or live threat hunting |

#### 1.3 Software Architecture

The platform follows a classic Manager-Agent architecture, augmented with a decoupled emulation framework. The Wazuh Manager serves as the central intelligence layer it ingests, parses, correlates, and alerts. Agents are lightweight forwarders deployed on each monitored endpoint. The Atomic Red Team framework operates orthogonally as an external stimulus layer, intentionally triggering the detection pipeline.

**Architecture Pattern: Centralized SIEM with Distributed Agents**
* **Wazuh Manager (Ubuntu Server):** Central rule engine, alert indexer (OpenSearch), and dashboard (Kibana fork).
* **Wazuh Agent (Windows 11 + Ubuntu 22.04):** Log collection, Sysmon event forwarding, ossec.conf configuration.
* **Emulation Layer (Atomic Red Team):** Isolated, controlled attack stimulus decoupled from the defensive stack.

*(All inter-component communication is encrypted with TLS 1.2+, self-signed certificates provisioned at install).*

**Component Interaction Overview**

| Component | Technology | Role in Platform |
| :--- | :--- | :--- |
| Wazuh Manager | Wazuh v4.x / OpenSearch | Central SIEM. Hosts the rule engine, alert indexer, and REST API. |
| Windows 11 Agent | Wazuh Agent + Sysmon | Primary attack target. Sysmon provides process-level telemetry depth unavailable from native Event Logs. |
| Ubuntu 22.04 Agent | Wazuh Agent + auditd | Secondary target for Linux-specific technique emulation (T1110 brute force, T1059.004 bash). |
| Atomic Red Team | PowerShell / Bash | Emulation framework. Executes isolated, technique-specific tests mapped directly to MITRE ATT&CK IDs. |
| SOC Dashboard | Wazuh Dashboard (Kibana) | Alert visibility, MITRE heatmap, agent health monitoring, rule management UI. |
| VMware Network | VMnet (Host-Only/NAT) | Network isolation boundary. Prevents emulation artifacts from reaching the host or internet. |

#### 1.4 Use Case Diagram

Three primary actors interact with the ThreatScopeLab platform:
1. 🕵️ **SOC Analyst:** Operates the defensive side authoring rules, validating detections, and investigating alerts.
2. 🥷 **Red Team Specialist:** Drives the offensive stimulus executing controlled emulation plans against target endpoints.
3. 🤖 **SIEM System (Wazuh):** Acts as an automated actor handling all continuous log processing, parsing & matching rules, and generating security alerts.

### 2. Database Design & Data Modeling

#### 2.1 Entity-Relationship (ER) Diagram

The data model reflects the core operational entities of the detection engineering lifecycle. An Agent generates Events. Events trigger Alerts when matched by a Custom Rule. Alerts are linked to MITRE Techniques through the rule that matched them. Emulation Plans capture the offensive side each plan targets a specific Agent and emulates a specific MITRE Technique, providing the ground truth for validating detection coverage.

#### 2.2 Logical Schema

> [!CAUTION]
> In the Wazuh deployment, most of this data is stored in the OpenSearch index (JSON documents). This relational schema is provided as a conceptual model for documentation and coverage tracking purposes.

**AGENT**
| Column | Type | Description | Constraint |
| :--- | :--- | :--- | :--- |
| `agent_id` | UUID | Unique identifier for the endpoint agent | PK, NOT NULL |
| `hostname` | VARCHAR(100) | Machine hostname (e.g., Win11-Agent) | NOT NULL |
| `ip_address` | VARCHAR(45) | Agent IP address (IPv4/IPv6) | NOT NULL |
| `os_type` | ENUM | Windows or Linux | NOT NULL |
| `status` | ENUM | Online / Offline / Disconnected | DEFAULT 'Offline' |
| `last_keepalive` | TIMESTAMP | Last heartbeat received from agent | NULLABLE |

**EVENT**
| Column | Type | Description | Constraint |
| :--- | :--- | :--- | :--- |
| `event_id` | UUID | Unique event identifier | PK, NOT NULL |
| `agent_id` | UUID | Source agent reference | FK -> AGENT, NOT NULL |
| `timestamp` | TIMESTAMP | UTC time of event generation on endpoint | NOT NULL |
| `log_source` | VARCHAR(100) | Source log channel (e.g., Sysmon/Operational) | NOT NULL |

### 3. Data Flow & System Behavior

#### 3.1 Data Flow Diagram (DFD)
The DFD illustrates how telemetry data originates at the endpoint layer, traverses the agent forwarding pipeline, and culminates in a security alert visible on the SOC Dashboard. The Atomic Red Team framework acts as the external stimulus that initiates the data flow by executing adversarial behavior on the target endpoints.

#### 3.2 Sequence Diagram - Detection Engineering Flow
The sequence diagram traces the complete lifecycle of a single detection event from the moment the Red Team Specialist fires an Atomic Red Team test through to the SOC Analyst seeing a validated alert on the dashboard. This is the core interaction pattern that the entire platform is built around.

**Key Data Flows Explained**
1. **Emulation -> Endpoint:** Atomic Red Team executes a test (e.g., `Invoke-AtomicTest T1059.001`), spawning a PowerShell process with an encoded command argument on the Windows 11 VM.
2. **Endpoint -> Sysmon:** Sysmon intercepts the process creation at the kernel driver level, generating Event ID 1 with full commandLine, parentImage, and hashes fields.
3. **Agent -> Manager:** The Wazuh Agent reads the Sysmon/Operational Windows Event Log channel (configured in ossec.conf) and forwards events to the Manager over TLS port 1514.
4. **Manager -> Rule Engine:** The ossec-analysisd daemon decodes incoming events and passes them through the rule tree. Custom rules in `local_rules.xml` are evaluated against parsed field values.
5. **Rule Engine -> Alert Index:** On a rule match, an alert JSON document is written to the OpenSearch index with the alert level, MITRE ID, description, and agent metadata.
6. **Index -> Dashboard:** The Wazuh Dashboard (Kibana fork) queries OpenSearch in real time, surfacing alerts in the Security Events view within seconds.

#### 3.3 Activity Diagram - Detection Engineering Loop
The activity diagram captures the decision-making workflow that underpins the project's methodology. It models both the success path (footprint found, rule written, detection validated) and the two primary failure paths: a telemetry gap (logging pipeline misconfiguration) and a false negative (rule logic too narrow or incorrect field targeting). The loop continues until all selected MITRE techniques are validated.

#### 3.4 State Diagram - Alert Lifecycle

> [!NOTE]
> Alerts in ThreatScopeLab have a well-defined lifecycle. Understanding these transitions is essential for SOC Analysts operating the platform - particularly the distinction between `MappedToMITRE` (emulation confirmed, rule validated) and `False Positive` (rule logic needs tuning). Both paths ultimately converge at `Resolved`, but with different implications for rule quality.

**Alert State Transition Table**

| From State | Trigger | To State | Actor Responsible |
| :--- | :--- | :--- | :--- |
| `[Initial]` | Wazuh rule match on incoming event | **Triggered** | 🤖 SIEM System |
| `Triggered` | Analyst opens alert in dashboard | **Acknowledged** | 🕵️ SOC Analyst |
| `Acknowledged` | Analyst begins raw log deep-dive | **Investigation Open** | 🕵️ SOC Analyst |
| `Investigation Open` | Emulation source confirmed in logs | **MappedToMITRE** | 🕵️ SOC Analyst |
| `Investigation Open` | Alert from benign activity or misconfigured rule | **False Positive** | 🕵️ SOC Analyst |
| `MappedToMITRE` | Detection documented, rule committed to GitHub | **Resolved** | 🕵️ SOC Analyst |
| `False Positive` | Rule tuned and re-validated via re-execution | **Resolved** | 🕵️ SOC Analyst / Detection Engineer |

#### 3.5 Class Diagram - System Components
The class diagram defines the logical structure of the ThreatScopeLab system in object-oriented terms. The `WazuhManager` is the central orchestrator, composing a `RuleEngine` and maintaining references to all active `Agents`. The `EmulationManager` is intentionally decoupled it drives the offensive stimulus independently, with its results visible only through the effects on the SIEM pipeline.

**Key Design Decisions in the Class Structure**
* The `RuleEngine.matchRule()` method returns a nullable Custom Rule no match returns null and the event is silently discarded, which matches Wazuh's actual behavior.
* `CustomRule.mitre_ids` is a list (not a single value) to accommodate sub-technique mapping (e.g., a single rule may cover both T1059 and T1059.001).
* `EmulationManager.recordResult()` explicitly captures the Detected/Missed outcome this is the primary metric for coverage gap analysis.
* `AlertIndex` is kept as a separate class from WazuhManager to reflect the architectural separation between the rule engine (ossec-analysisd) and the storage layer (OpenSearch).
